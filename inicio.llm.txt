# 1. MISSÃO DO PRODUTO

O AECS é um sistema de controle para engenharia de software agêntica.

Ele deve ficar entre:

* humano;
* coding agent;
* modelo de IA;
* repositório;
* ferramentas;
* verificadores;
* CI/CD.

O AECS não é um chatbot e não é um clone de Copilot.

Sua função é:

1. receber uma intenção humana;
2. transformá-la em um `TaskContract`;
3. definir limites de execução;
4. executar um coding agent em ambiente controlado;
5. observar tudo o que o agente faz;
6. limitar custo, tempo, escopo e retries;
7. capturar a alteração produzida;
8. verificar a alteração;
9. produzir evidências;
10. decidir entre:

* VERIFIED;
* REJECTED;
* HUMAN_REVIEW_REQUIRED.

Princípio fundamental:

> Probabilistic Discovery. Deterministic Enforcement.

Modelos podem sugerir e raciocinar.

Regras críticas devem ser verificadas deterministicamente sempre que possível.

# 9. PRIMEIRO AGENT ADAPTER

Implemente somente UM adapter inicialmente.

O adapter deve ser provider-agnostic do ponto de vista do domínio.

Toda dependência específica de fornecedor deve ficar isolada em Infrastructure ou AgentRuntime.

O domínio não pode depender de SDK de OpenAI, Anthropic, GitHub ou qualquer fornecedor.

O primeiro adapter precisa retornar:

* stdout;
* stderr;
* status;
* duração;
* tokens quando disponíveis;
* custo estimado;
* arquivos modificados;
* exit reason.

Não permita que detalhes do provider vazem para o domínio.

---

# 10. SANDBOX

A execução do coding agent deve ocorrer de forma isolada.

Na primeira versão utilize Docker.

Cada execução deve possuir:

* workspace temporário;
* clone/cópia isolada do repository;
* timeout;
* limites de execução;
* processo descartável;
* captura de stdout;
* captura de stderr.

Não dê acesso irrestrito ao host.

Não dê acesso a secrets permanentes.

Não dê acesso irrestrito à rede se não for necessário.

---

# 11. CONTROL KERNEL

O `ControlKernel` deve ser responsável por enforcement.

Implemente inicialmente:

## Budget enforcement

Verifique:

* tempo;
* retries;
* quantidade de arquivos modificados;
* custo quando disponível.

## Scope enforcement

Exemplo:

```text
Allowed:
src/Customers/**
tests/Customers/**
```

Se o agente modificar:

```text
src/Billing/**
```

a execução deve ser marcada como:

```text
ScopeViolation
```

Não peça a um LLM para decidir isso.

Faça deterministicamente.

---

# 12. CIRCUIT BREAKER

Implemente limites configuráveis:

```text
MAX_COST
MAX_TOKENS
MAX_FILES_CHANGED
MAX_RETRIES
MAX_DURATION
```

Quando um limite for ultrapassado:

1. interrompa a execução;
2. registre a razão;
3. crie Evidence;
4. atualize o estado corretamente.

---

# 13. VERIFICATION DAG V0.1

Implemente inicialmente apenas:

## BuildVerifier

Executa:

```bash
dotnet build
```

## UnitTestVerifier

Executa:

```bash
dotnet test
```

## ScopeVerifier

Verifica se o diff respeita o TaskContract.

## BudgetVerifier

Confirma se budget foi respeitado.

Não crie ainda um LLM verifier.

Cada verifier deve produzir `VerificationResult`.

---

# 14. DECISÃO FINAL

Regra inicial:

```text
Todos os verificadores obrigatórios PASS
→ VERIFIED
```

Se uma regra determinística obrigatória falhar:

```text
→ REJECTED
```

Se a mudança estiver tecnicamente válida, mas exigir decisão humana conforme ApprovalPolicy:

```text
→ HUMAN_REVIEW_REQUIRED
```

Mantenha a regra simples.

---

# 15. EVIDENCE

Exemplos:

```text

BudgetExceeded

TestsFailed

VerificationFailed
```

O objetivo é que posteriormente seja possível reconstruir exatamente:

> o que aconteceu nessa execução?

# 22. REGRAS DE DESENVOLVIMENTO

1. Faça mudanças pequenas.

2. Não implemente funcionalidades futuras “porque serão úteis depois”.

3. Evite abstrações especulativas.

4. Toda nova dependência deve ter justificativa.

5. Não utilize padrões arquiteturais apenas por moda.

6. Prefira código explícito.

7. Mantenha o domínio independente de fornecedores.

8. Documente decisões irreversíveis com ADR.

9. Se encontrar ambiguidade, escolha a solução mais simples compatível com o documento de fundação.

10. Não reescreva partes funcionando sem justificativa.

11. Não adicione frontend nesta fase.

12. Não introduza IA onde uma regra determinística resolve o problema.
